# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

volamos runs classic AmigaOS m68k **CLI** binaries natively on
macOS/Linux by emulating only the CPU and reimplementing library calls at
the API boundary — a Wine-style high-level runtime, not a full-system
emulator. No GUI, no custom chips, no ROM. It is a Rust successor to
`vamos` (amitools). Target compatibility: Kickstart/Workbench 3.1 and
later-3.x behavior, verified empirically against real binaries.

## Project layout

Rust 2024 Cargo workspace, two crates:

- `crates/volamos-core/` — the runtime: CPU/memory abstractions, HUNK
  loader, trap dispatch, and all AmigaOS library handlers. Most unit
  tests live here, beside the code they cover.
- `crates/volamos/` — the CLI binary: clap-based arg parsing in
  `main.rs`, `.volamos` config-file loading in `config.rs`.

Also: `fixtures/` (tiny committed guest binaries, their `.s` sources, and
`gen_*.py` generators), `userdocs/` (the MkDocs user-facing site),
`tools/` (comparison harnesses and `gen_lvos.py`), `docs/plan.md` (phase
breakdown and status history), `assets/`.

## Commands

```sh
cargo build --workspace
cargo test --workspace                  # unit + integration
cargo test -p volamos-core dosargs::    # one module's tests
cargo test -p volamos --test phase3_e2e # one integration test file
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
mkdocs build --strict                   # required when userdocs/ changes
mkdocs serve                            # preview the docs site
cargo run -p volamos -- fixtures/hello  # quick manual run
```

CI checks formatting, Clippy, tests on Linux and macOS, the strict docs
build, the comparison harnesses, and the Docker image.

Useful runtime flags while debugging a guest: `--verbose` (every
dispatched library call), `--snoop` (only resource opens: libraries,
files), `--sanitize` (+ `--sanitize-uninit`), `--stack-report`,
`--cpu`/`--fpu`, `--no-jit`, `-V VOL:/host/dir`, `-a ASSIGN:path`.

Comparison harnesses in `tools/`: `compare_vamos.py`, `compare_jit.py`
and `compare_docker.py` run in CI; `compare_three_way.py`,
`compare_kickstart_versions.py` and `compare_amitools_suite.py` are
local-only — they need a real ROM, real Workbench media, or an external
checkout.

## Architecture

**The trap-dispatch core (`dispatch.rs`)** is the piece to understand
first; its module doc is the authority. Real AmigaOS calls go `jsr
-LVO(a6)` through a jump table below a library base. volamos plants an
A-line opcode word (`0xA000 | slot`) at `base + lvo`, the `m68k` crate
surfaces A-line opcodes as `StopReason::Trap` rather than taking a
hardware exception, and `Runtime::run` decodes the slot, calls the
registered `LibraryHandler`, then performs the `RTS` itself in host code.
Program exit is the same mechanism: the initial stack's return address is
`EXIT_STUB_ADDR`, which also traps.

- `cpu.rs` — `Cpu` trait (registers, step/run, trap kinds) so the
  emulator backend is swappable; `backend.rs` — the `m68k` crate behind
  it, including the JIT/`run_batch` fast paths.
- `memory.rs` — `FlatMemory`, big-endian flat guest address space; also
  hosts the optional sanitizer shadow map (inline, not a wrapper type,
  because `Cpu::Memory` is one concrete associated type).
- `guestmem.rs` — `GuestHeap` plus BPTR/BSTR/C-string helpers. All guest
  allocation funnels through here, which is what makes `--sanitize` cheap.
- `lvos/` — per-library LVO metadata tables (name, offset, argument
  registers), **generated by `tools/gen_lvos.py` from AROS interface
  descriptions**; don't hand-edit. Handlers are registered by *name*
  against these tables, and they also power "unknown call" diagnostics
  that name the function a guest tried to call.
- `exec*.rs`, `dos*.rs`, `utility.rs`, `locale.rs`, `intuition.rs`,
  `mathlibs.rs`, `bsdsocket.rs`, `graphics.rs` — the handlers themselves,
  split by subsystem (e.g. `dosfile`/`doslock`/`dosargs`/`dospattern`/
  `dosseg`/`dospkt`). Each subsystem exposes a `register_*_handlers(table,
  mem)` function using the `reg!("Name", handler)` macro pattern in
  `dosfile.rs::register_dos_handlers`; `Runtime::new` calls them.
- `loader.rs` — AmigaOS HUNK executable loading, relocation, and debug
  hunks (symbol + `file:line` info used by sanitizer reports).
- `vfs.rs` — host-backed volumes/assigns, Amiga `:`/`/` path semantics,
  multi-assign search order; `dosmeta.rs` — `.uaem` sidecar files for
  protection bits and comments.
- `taskswitch.rs` — **cooperative, non-preemptive** scheduler added for
  `CreateNewProc`. Switches happen only at specific handler-requested
  points (blocking `Wait`, `Signal` waking a blocked task, `Permit` after
  `Forbid`+`SFB_SAR`, `SetTaskPri`). Deadlock is reported loudly, never
  hung — that "fail loudly instead of hanging the host" posture runs
  throughout the runtime.
- `ContinuationStack` in `dispatch.rs` — the trampoline primitive for
  handlers that must call *guest* code re-entrantly (disk-library init
  vectors, `RunCommand`). A handler pushes a host closure plus a guest
  entry address; the generic post-dispatch `rts` re-enters the closure
  when the subroutine returns. Register discipline (notably restoring the
  caller's `A6`) is the calling handler's job, not the primitive's.
- `sanitize.rs` — redzones, free quarantine, below-SP checks, shadow call
  stack, byte-granular uninit tracking. It is a *detector*: violations are
  grouped by PC and reported at exit, never abort the guest.
- `uaedebug.rs` / `uaelibdebug.rs` / `emu68debug.rs` — magic-address debug
  output hooks compatible with UAE/emu68 conventions.

## Working on this codebase

- **Behavior comes from ground truth, not guesses.** The existing code
  cites its sources inline (NDK 3.2 autodocs, RKRM, AROS, disassembly of
  real binaries, real-hardware runs via Copperline). When implementing or
  fixing a call, cite where the semantics came from in the doc comment,
  and prefer a verified constant over a plausible one. Keep emulator
  behavior close to documented AmigaOS semantics. Where volamos and
  `vamos` disagree and hardware settled it, that goes in
  `userdocs/Differences-from-vamos.md`.
- Module-level doc comments here are long and load-bearing — they record
  *why* a design is as it is. Read the relevant one before changing a
  module, and keep that style when adding one.
- Unit tests live beside the implementation; end-to-end tests in the
  relevant crate's `tests/`. Name tests for the behavior or regression
  they demonstrate, and add regression coverage for every behavioral fix.
- **The user docs are part of the change, not a follow-up.** Every
  `fix:`/`feat:` PR that touches `crates/**` either updates a page under
  `userdocs/` or states why none applies — don't leave the question
  open. Map the change to its page:

  | What changed | Page |
  | --- | --- |
  | CLI flags, arguments, exit behavior | `userdocs/CLI-Reference.md` |
  | library/handler or device coverage | `userdocs/Supported-Libraries.md` |
  | volume, assign or Amiga-path rules | `userdocs/Volumes-and-Assigns.md` |
  | `.volamos` config keys or lookup order | `userdocs/Configuration.md` |
  | a vamos disagreement hardware settled | `userdocs/Differences-from-vamos.md` |
  | a worked invocation worth showing | `userdocs/Examples.md` |
  | install/build/run surface | `userdocs/Installation.md`, `Building-from-Source.md`, `Getting-Started.md` |

  Run `mkdocs build --strict` whenever `userdocs/` changes. An internal
  fix with no user-visible surface is a legitimate answer — put it in
  the PR body as a `Docs:` line (e.g. `Docs: n/a — internal
  pr_ReturnAddr frame layout, no user-visible surface`) or apply the
  `no-user-docs` label. The `User docs decision` CI check enforces
  exactly that choice, and `.claude/hooks/check-user-docs.sh` raises it
  mid-session. `userdocs/Changelog.md` is **never** the answer: it is
  release-please's file and is never hand-edited.

## Commits and pull requests

All changes land through a PR against `main` — never commit to `main`
directly. PRs are squash-merged with the PR title as the commit subject,
so **every PR title must be Conventional Commits**:
`<type>(<scope>): <description>`. The `PR title` CI check enforces it.

`feat` bumps the minor version, `fix` the patch, and a `!` or
`BREAKING CHANGE:` footer the major; `docs`, `test`, `chore`, `refactor`,
`perf`, `build`, `ci`, `style`, `revert` parse but trigger no release.
Scope is the subsystem: `exec`, `dos`, `cli`, `backend`, `loader`,
`sanitize`, `mathlibs`, `bsdsocket`, `docs`, `release`. Example:
`fix(exec): queue ObtainSemaphore waiters on ss_WaitQueue`.

Keep each commit focused. PRs should explain the user-visible behavior or
fix, link relevant issues, summarize notable changes, and list checks run.

Releases are automated: release-please keeps a release PR on `main` that
accumulates `feat:`/`fix:` changes; merging it bumps both crate versions,
updates `Cargo.lock` and `userdocs/Changelog.md`, tags the release, and
publishes binaries, the Docker image, and docs. **Never hand-edit
versions or the changelog.**
