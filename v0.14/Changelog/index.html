    Changelog¶

    This page tracks major milestones during development, following the version scheme in Cargo.toml.

    0.14¶

    • exec.library's ObtainSemaphoreShared/AttemptSemaphoreShared implemented (issue #189) — libpthread's pthread_getspecific/ pthread_setspecific take a shared lock, and libstdc++ calls them on every throw when gcc is built with --enable-threads=posix, so every C++ program built that way stopped at its first throw with "unhandled library call" (952 of 960 failures in the m68k-amigaos-gcc C++ testsuite). Semantics follow AROS's rom/exec/semaphores.c: both route through the same InternalObtainSemaphore/InternalAttemptSemaphore as their exclusive counterparts with a NULL owner, so a free semaphore obtained shared gets ss_Owner = NULL, and a shared or exclusively-held semaphore blocks/fails the same way the exclusive calls already do.

    • dos.library's GetArgStr/SetArgStr and exec.library's SetTaskPri implemented (issue #193) — both were in the LVO tables without handlers, so no program built with clib2 (m68k-amigaos-gcc -mcrt=clib2) could run: its startup code calls GetArgStr to read the command line and its exit code calls SetTaskPri to restore the priority the startup saved. GetArgStr returns pr_Arguments (the same buffer Runtime::new/ RunCommand already populate); SetArgStr stores D1 there and returns the old value, the same pattern as GetFileSysTask/ SetFileSysTask; SetTaskPri stores the new priority in ln_Pri and returns the old one sign-extended (nothing to reschedule with only one task).

    • ReadArgs/FindArg fixes (issue #203): a host argument like ITER=0 is no longer force-quoted just because it contains =, so volamos -- prog ITER=0 now means what prog ITER=0 means in a shell — the keyword ITER with value 0 — matching AmigaOS and vamos; and a template keyword with more than two =-separated names (HELP=--help=-h/S) now matches every name, not just the first two. Also, ReadArgs(NULL) now reads the command line from the process's Input() filehandle buffer the way RunCommand actually populates it, instead of the guest's own A0/D0 startup buffer — which C startup code (e.g. vbcc's) edits in place while splitting it into argv, corrupting a later ReadArgs(NULL) call that read the same memory.

    • timer.device's GetSysTime/ReadEClock resolve real microseconds — without --clock-mhz, both (and Intuition's CurrentTime) took the host time through now_as_datestamp()'s 1/50 s ticks, so every tv_micro was a multiple of 20000 and every interval a program timed was a multiple of 20 ms, making --jit timings useless for short runs. host_time_secs_micro() now reads SystemTime directly and keeps real subsec_micros(); DateStamp is unchanged.

    • Fixed a test race (issue #210): Runtime::run's dispatch loop only folds the process-global pending-host-break flag when a new Runtime::enable_host_break_folding() opt-in is set (the real CLI sets it; test-only Runtimes built by unrelated test modules don't), so unrelated tests calling Runtime::run in parallel can no longer clobber the two dedicated host-break tests' state.

    0.13¶

    • ixemul.library-linked programs run a full round of path-based file I/O (issues #186, #196) — ixemul's __plock() resolves every path itself via GetDeviceProc() then raw DosPackets sent straight to dvp_Port, which this runtime left NULL, so every path-based call (open(), mkdir(), stat(), rename(), unlink(), opendir()) failed with ENOENT before any packet was even sent. GetDeviceProc now returns the same synthetic filesystem packet port every lock's fl_Task/handle's fh_Type already does. With a real destination, handle_fs_packet now answers the rest of the path actions ixemul sends — ACTION_CREATE_DIR, ACTION_DELETE_OBJECT, ACTION_RENAME_OBJECT, ACTION_MAKE_LINK (hard and soft), ACTION_SET_PROTECT, ACTION_SET_DATE, ACTION_SET_OWNER, ACTION_SET_FILE_SIZE, ACTION_WAIT_CHAR, and ACTION_DISK_INFO — plus dos.library's Info() call ixemul makes when resolving a path through /. An unknown packet action's Res1 is now DOSFALSE rather than -1, which a caller reading it as a boolean (ixemul's mkdir()) previously misread as success. Verified against the real ixemul.library 80.1 SDK: a test program covering mkdir, open/create, read/write/lseek, fstat, ftruncate, O_APPEND, O_EXCL, ENOENT, rename, opendir/readdir, unlink, and rmdir now passes all 21 checks on --cpu 68000 and 68020, with and without --sanitize.

    • exec.library's Supervisor() enters its routine through a real exception frame (issue #192) — it used to push a 6-byte 68000 frame regardless of the emulated CPU, so a 68010+'s RTE (which reads a format word after the PC) ran off the end of guest memory on --cpu 68020/68040. Supervisor() now switches to supervisor mode and the supervisor stack and pushes the frame the model's RTE actually pops — SR, PC, and on a 68010+ a format-0 vector word — the same way a real hardware exception does. This also fixes a second, independent gap: the routine may now make its own library calls and RTE anywhere, not just back to its caller, which unblocks ixemul.library's expunge() cleanup (sigreturn()'s Supervisor()-based longjmp()) on normal program exit. gcc's setjmp/longjmp execute-testsuite cases now pass against both ixemul 47.3 and 80.1 at every optimization level.

    • libnix's clock() no longer crashes — it reads DOSBase->dl_TimeReq->io_Device directly and calls through it at ReadEClock's LVO instead of going through OpenDevice/DoIO, a documented RKRM idiom real dos.library relies on internally. dl_TimeReq previously held whatever the sentinel prefill left there; it's now a real timerequest pointing at timer.device, exactly as an explicit OpenDevice("timer.device") already produces.

    • AllocDosObject/FreeDosObject gain the two remaining <dos/dos.h> types: DOS_STDPKT (a StandardPacket linked the documented way for SendPkt/WaitPkt) and DOS_CLI (a CommandLineInterface with its four BSTR buffers sized per <dos/dostags.h>'s ADO_*Len tags). Every object type the header defines is now implemented.

    • Fixed a guest-heap leak in Lock's new_lock: if allocating the synthetic filesystem port failed right after the FileLock struct itself was allocated, the FileLock block was never freed.

    0.12¶

    • ixemul.library-linked programs run file I/O (issue #186) — ixemul's __open() does AllocDosObject(DOS_FILEHANDLE) for a FileHandle of its own, then drives the rest of the I/O with raw DosPackets sent straight to a handler's message port instead of further library calls (the same packet-level idiom issue #24's sc1.library fix already covers for ACTION_READ/WRITE/SEEK/ END). AllocDosObject(DOS_FILEHANDLE)/FreeDosObject are now real (reusing the same FileHandle allocation Open itself uses, with bookkeeping so a later explicit FreeDosObject doesn't race a packet-driven Close), and handle_fs_packet now also answers ACTION_LOCATE_OBJECT (the packet-level Lock), ACTION_FINDINPUT/ ACTION_FINDOUTPUT/ACTION_FINDUPDATE (the packet-level Open), ACTION_EXAMINE_FH, and ACTION_READ_LINK (reusing the real host-symlink support issue #160 added). Every lock's fl_Task now points at the same synthetic handler port a FileHandle's fh_Type does, since ixemul's __plock() sends ACTION_LOCATE_OBJECT straight to a lock's own task to resolve path components — the real, documented AmigaOS idiom. Verified against the real ixemul.library 80.1 SDK (Aminet dev/lib/ixemul-80.1-m68k.lha): a program linked against it now runs to completion of its own logic (see issue #192 for a separate, still-open gap in its exit cleanup path).

    • m68k crate bumped to 0.14.7 — fixes three real FPU correctness bugs, all traced to the crate's old lossy extended-to-double/single conversion and extended-format exponent handling:

      • Issue #150: values below 2^-16382 were off by a factor of two (the crate read a biased exponent of 0 the x87 way, "treat it as if biased 1"; the MC68881 reads it as 2^-16383 with the integer bit still stored — M68000 PRM Table 1-6), and FDIV/FSQRT truncated instead of rounding to nearest.
      • Issue #155: FMOVE from an FP register to .d/.s/an integer format truncated instead of rounding — every hard-float double a program stores was up to 1 ulp off, rounded toward zero.
      • Issue #181: a denormal double round-tripped through an FP register (fmove.d <mem>,fp0 then back out) came back as zero.

    Verified directly against each issue's own repro values (hand-built m68k instruction sequences) rather than just trusting the upstream changelog — all three now match the expected bit patterns exactly, including FDIV's correctly-rounded last digit. Found and fixed via the gcc toolchain's test suite running under --cpu 68020 --fpu.

    • Three ixemul.library 80.1 startup gaps fixed (issue #178) — with issue #175's AllocEntry and the --libs-dir vector-table cap raise already in place, an ixemul-linked program's library-init path still stopped on three more calls: dos.library's StartNotify/EndNotify (unhandled — ix_init.c's ENV: watch now fails cleanly with ERROR_ACTION_NOT_KNOWN, which it already tolerates, instead of crashing the run); AddIntServer(INTB_VERTB) (refused on principle before — ix_open.c adds one unconditionally on every OpenLibrary, so VERTB is now accepted and tracked, though still never fired, since there's still no VBlank tick model); and pr_ReturnAddr/cli_DefaultStack (never populated — ixemul's stack-extension logic follows the real RunCommand convention for both, and with them left at zero it always "extended" the stack using bounds computed from address zero, corrupting the live stack mid-copy; both are now laid out for real, right below the exit-stub return address already at the initial sp).

    • --sanitize no longer false-positives on fmovem.x <list>,-(sp) (issue #180) — the below-stack-pointer "grace band" that forgives a push's own store landing below the stack pointer before the run loop republishes it was sized for movem.l's widest push (16 integer registers, 64 bytes), but fmovem.x can push up to 8 FPU registers at 12 bytes each (96-bit extended precision) for 96 bytes — wider than the band, so a 6-register FP-register-save prologue (gcc's own) flagged its deepest bytes as invalid. The band is now 96 bytes.

    0.11¶

    • AllocEntry/FreeEntry implemented (the other half of issue #175) — ixemul.library's init calls AllocEntry() right after reading its environment variables, which was the first unhandled library call on the way to running -mcrt=ixemul binaries. Each entry is allocated exactly as AllocMem would with that entry's own MEMF_* requirements (MEMF_CLEAR honoured per entry), failure returns the failed entry's requirements with bit 31 set (the documented, unusual convention), and a partial failure backs out fully — the post-SetPatch behavior that's been ROM since V36, not the leaky V1.x one the autodoc's BUGS section describes. Blocks handed out get the full --sanitize treatment (redzones, uninitialised marking, use-after-free on FreeEntry), same as AllocMem's.

    • --cpu 68040/68060 now default to the full chip with its on-die FPU present (issues #174/#175) — after #167's fixes, a plain --cpu 68060 (no --fpu) inherited the global no-FPU default and ran as an FPU-less 68060, so an ordinary -m68020-60 -m68881 binary died on its first FPU instruction unless --fpu was spelled out, while the equivalent plain --cpu 68040 ran it fine — the two full chips disagreeing about the same default. Both now resolve the FPU as present unless --no-fpu is given explicitly (--cpu 68040 --no-fpu still substitutes to 68ec040; --cpu 68060 --no-fpu still selects the genuinely FPU-less 68LC060/68EC060 with the clean vector-11 stop). With the FPU present, AttnFlags now also reports AFF_68881|AFF_68882 alongside AFF_FPU40, matching a real 68040/68060 system booted with SetPatch — programs commonly test AFF_68881 alone to mean "an FPU is present" (ixemul.library's init is one); the FPU-less 68060 case advertises no FPU bits at all, as a real LC/EC060 machine does.

    • --libs-dir can load libraries with large vector tables, like ixemul.library (issue #171) — the loader's "treat an unterminated vector table as corrupt rather than scanning forever" safety cap was 256 entries, comfortable headroom for an ordinary AmigaOS library (dos.library has about 170) but too small for a shared C library: ixemul.library exports around 720 functions, so loading it via --libs-dir was refused outright as "corrupt" even though the file is fine. Raised to 1024. Whether ixemul-linked binaries actually run under volamos afterward is a separate, unexamined question (it wants a real process environment this runtime doesn't fully provide) -- this only fixes the loader's own refusal to read the file.

    • --cpu 68040 --no-fpu now behaves correctly instead of silently doing nothing, and --cpu 68060 --no-fpu no longer crashes (issue #167, both halves) — the full 68040/68060 always have their on-die FPU on real hardware (there's no plug-in-68881 option to leave out, unlike 68020/68030), so before this fix the CPU core kept executing every FPU instruction regardless of --no-fpu while AttnFlags told the guest there was no FPU, a combination no real chip has. --cpu 68040 combined with an explicit --no-fpu now runs as --cpu 68ec040 instead — the model that really has no FPU at all — printing a one-line note; pass --cpu 68ec040/68lc040 directly to skip it. AttnFlags' AFF_FPU40 bit is now also unconditional for --cpu 68040/68060 (previously gated on --fpu, which was itself the source of the lie). --cpu 68060 --no-fpu had a separate, deeper bug: the m68k crate's own internal 68060 FPU-disabled exception delivery bypasses this runtime's usual guest-exception interception entirely, landing on whatever garbage happened to sit at vector 11's slot and manifesting as a baffling "continuation stub trapped ... with no pending continuation" — now mitigated by pre-seeding that vector with a dedicated stub that reports a clean, attributable stop instead, without affecting any other --cpu/--fpu combination's existing (correct) behavior, including a guest that installs its own real FPU-probe handler there.

    • --sanitize now reaches exec.library's Allocate/Deallocate (issue #83, Tier 1) — a successful Allocate marks its returned block uninitialized and Deallocate poisons the freed block as used-after-free, the same shadow-map states the AllocMem/AllocVec family already got. This matters because a C program's malloc (under both libnix and newlib) takes a few big blocks via AllocVec and then sub-allocates from its own pool with Allocate, so most of a real C program's heap traffic was previously invisible to the detector entirely. No redzones yet (that's Tier 2, a separate, bigger decision noted in the issue) — so a malloc overrun one byte past the end of a block still isn't caught, only use-after-free and uninitialized reads. See --sanitize.

    • FINT/FINTRZ no longer trap under --cpu 68060 — the m68k CPU core crate's 68060 model wrongly treated both as unimplemented in hardware (true of the 68040, but the 68060 brought them back), so a correctly built 68060 binary that used them — GCC emits FINTRZ for -m68060, and libm's exp() hits it — died with an unimplemented- instruction exception under --cpu 68060 --fpu, with or without --fpsp-emulate. Fixed upstream and picked up by the crate update to 0.14.5; there is no volamos-side change. The transcendentals, FMOD/FREM/FSCALE, FGETEXP/ FGETMAN, FSINCOS and the other genuinely removed instructions still trap as on real hardware. This clears the known issue listed in the v0.10 release notes.

    • --uae-debug: UAE's debug sprintf port (issue #140) — a program that formats debug text with plain stores to 0xBFFF00 (the channel WinUAE/amiberry expose as debug_mem) now gets that text on stderr instead of nothing: a store at +0 pushes an argument, a long store at +4 prints a format string, a long store at +8 switches to a va_list-style argument block in guest memory. Format codes are %% %c %s %b %p %x %X %d %i %u %o with C flags, width and precision; integers are 16-bit unless the directive has an l. The 68000/68010 word-pair stores UAE latches are honoured. The port works whatever --ram is (stores are intercepted before the memory lookup), its 12 bytes are kept out of the guest heap, --sanitize does not report stores to it, and it forces --no-jit like --sanitize does. Off by default and CLI-only; nested System()/Execute() runs inherit it. The same flag also enables the uaelib log call below.

    • --uae-debug: UAE's uaelib debug-log trap (issue #140) — with the flag on, a C-style call to 0xF0FF60 (calltrap(86, "message") as declared in amiberry's uae_pragmas.h, used by e.g. the vscode-amiga-debug toolchain) writes DBG: message to stderr and returns 1 in D0 (0 for a bad pointer). Only mode 86 is implemented; any other mode returns 0 with a one-time-per-mode warning. It is a code address, so it needs --ram of 16 MiB or more (a startup warning says otherwise); its two bytes are kept out of the guest heap, it works on every --cpu, and with the flag off nothing changes.

    • --emu68-debug: Emu68's debug byte port (issue #140) — a byte-sized store to the absolute address 0xDEADBEEF (the debug console of Emu68, the PiStorm JIT) now writes that byte to stderr, raw: no newline or prefix added. Word and long stores there stay ordinary memory. Needs a 32-bit CPU (--cpu 68020 or later): the 68000/68010 present 0x00ADBEEF, so the port never triggers and a startup warning says so. Off by default and CLI-only; forces --no-jit like --uae-debug, composes with it, and is inherited by nested runs.

    • SIGTERM and a second SIGINT now force-exit immediately (issue #151) — volamos could keep running after SIGTERM/SIGINT if the guest never made a library call: host signals are only folded into the guest as a cooperative SIGBREAKF_CTRL_C at a dispatched library-call boundary, so a tight, call-free guest loop could never observe either. SIGTERM now terminates the process on receipt -- it means "terminate", not "ask the guest nicely" -- exiting with the shell's usual 128 + SIGTERM (143). A second SIGINT (arriving before the first was folded into the guest) also force-exits, matching the double-Ctrl-C "I mean it" convention most interpreters use, exiting 128 + SIGINT (130). A single SIGINT keeps the existing cooperative-delivery behavior, unchanged. Both forced paths use _exit directly from the signal handler.

    • --cache: an opt-in direct-mapped instruction-cache model (issue #148) -- --clock-mhz timings treated every instruction fetch as a free cache hit, so cache-thrashing effects never showed up: a loop bigger than the 68020/030/060's on-chip cache, -Os vs -O2 code-size trade-offs, block duplication, etc. all cost nothing. --cache adds a real direct-mapped model, sized by --cpu (256 bytes on 68020/68030, 4096 on 68040/68060), wired into the m68k crate's own cache-aware cycle tables. CacheClearU/CacheClearE now actually invalidate the model instead of being pure no-ops. Off by default, so existing --clock-mhz numbers stay comparable. Known limitations: no effect on --cpu 68040 (the crate's 68040 timing model doesn't consult cache state at all yet), CacheControl's CACRF_EnableI toggle isn't wired to the model, and data-cache/ memory-wait-state modeling (also proposed in #148) is explicitly not included -- left as a follow-up.

    • RunCommand() now really overlays the calling process (issues #8 and #156) -- it used to run the invoked seglist through a brand-new Runtime/CpuCore/FlatMemory, the same path System()/ Execute() use (correct for those two, which really do spawn independent processes on real hardware, but wrong for RunCommand: real AmigaOS runs it as a subroutine in the caller's own process, inheriting whatever the caller left in its registers -- FPCR/ FPSR included -- and leaving its own writes behind for the caller to see afterward). RunCommand now resolves the entry point directly from the already-LoadSeg'd bytes in guest memory, carves a stack region from the caller's own heap, and runs the invoked program through the ordinary dispatch loop via the trampoline primitive, resuming the caller once it returns with D0 as the exit code. System()/Execute() are unaffected -- they keep the nested- Runtime path. A real consequence of running on the same CPU: no register is actually safe across a RunCommand call, matching real hardware (a program invoked this way is free to clobber D0-D7/ A0-A6 exactly as it pleases).

    • dos.library: ExamineFH, DupLockFromFH, ParentOfFH, GetCurrentDirName, SetFileSize, SplitName, SetProgramName (issue #159, "Tier 1") -- codewiz's newlib-porting feedback flagged that volamos 0.10 aborted the program on several dos.library calls a real libc port needs: fstat() had to fall back to Seek, getcwd() to Lock("")+NameFromLock, and link()/symlink()/fchdir() were implemented but excluded from CI pending a real-AmigaOS run. These seven are the calls that were genuinely cheap to add because they reuse infrastructure that already existed (Examine/Lock's own fill_fib/new_lock helpers, Vfs::cwd(), Seek's offset-mode resolution, GetProgramName's own BSTR handling) rather than needing new capability.

    • dos.library: OpenFromLock, ChangeMode (issue #159, "Tier 2") -- cheap in the same sense as Tier 1 above, but needed a small refactor first: DosState::open was split into its VFS-resolution step and a reusable open_resolved that OpenFromLock could call directly on an existing lock's already-resolved path, relinquishing the lock on success.

    • dos.library: MakeLink, ReadLink, LockRecord/LockRecords/ UnLockRecord/UnLockRecords (issue #160, "Tier 3") -- the remaining, genuinely new-capability half of codewiz's feedback above. MakeLink maps real AmigaOS "soft link"/"hard link" semantics onto a real host symlink/hard link (soft != FALSE creates a symlink via std::os::unix::fs::symlink, pointing at a target that need not exist yet, matching real soft links' documented "resolved lazily" semantics; soft == FALSE creates a std::fs::hard_link from an existing lock). ReadLink reports a real host symlink's raw target string back to the caller. This runtime deliberately does not implement the real AmigaOS-level "filesystem returns ERROR_IS_SOFT_LINK, DOS calls ReadLink, retries" protocol inside Lock/Open/Examine -- a host symlink already resolves transparently through ordinary host filesystem calls, so those calls "just work" on a soft link without it. Symlink creation is Unix-only; on other targets MakeLink's soft-link half reports a clean IoErr() rather than attempting a host call that would need elevated privileges/Developer Mode. LockRecord/LockRecords/UnLockRecord/ UnLockRecords (byte-range record locking) are cheap, always- succeeds stubs -- this runtime models no real concurrency, so there's nothing a record lock could actually enforce.

    0.10¶

    • Cause() software interrupts, and loud interrupt-registration stubs (issue #136) — exec.library's Cause now works for real: the node is marked NT_SOFTINT (a node already pending is ignored, with no nest count), queued on one of exec's five priority levels (-32/-16/0/+16/+32 from ln_Pri, truncating in-between values; a priority outside -32..=+32, a NULL node or a NULL is_Code stops the run with an error, before the node is touched), and its handler runs before Cause returns — highest priority first, FIFO within a level — with A1 = is_Data, A5 = is_Code, A6 = ExecBase. A Cause made from inside a handler is queued and runs once the current handler returns; the node type goes back to NT_INTERRUPT just before its handler is entered. The caller's A5 and A6 are restored after the queue drains. Disable/Enable still keep no nest count, so a Cause inside a Disable section runs its handler immediately instead of at Enable. SetIntVector, AddIntServer and RemIntServer now stop the run with a message naming the requested INTB_* interrupt and explaining that this runtime never delivers hardware interrupts, rather than the generic unhandled-call text. These are deliberately not "register and ignore": a server that never fires would hang or misbehave far from the cause. Asynchronous interrupt delivery (VBlank, timers, CIA) is not implemented.
    • Non-RTF_AUTOINIT disk libraries, and the exec.library calls their init code needs (issue #133) — OpenLibrary can now load an NT_LIBRARY whose struct Resident has no RTF_AUTOINIT flag, the shape real Kickstart modules such as graphics.library use: rt_Init is code that is called directly (D0 = 0, A0 = segList, A6 = ExecBase, as InitResident does) and builds the library itself, returning the base in D0. Previously this was rejected with "Resident isn't RTF_AUTOINIT". If the routine adds itself to LibList but returns NULL, the library is found there by its Resident name; if it does neither the open is refused. The loader no longer double-links a library that already called AddLibrary, and since such a library owns its base's memory (its Close/Expunge code frees it, as on real exec) the host never frees or unlinks it a second time on the last close. New guest-callable MakeLibrary (runs its init routine too), MakeFunctions, InitStruct (the full exec/initializers.i byte-command interpreter, which also means an RTF_AUTOINIT library's non-NULL InitStruct table is now applied instead of rejected) and AddLibrary (links the node into LibList by priority and makes it openable by name, with no disk file). Also added alongside, since a hand-rolled init commonly reaches for them: SumLibrary (checksums the jump table's vector addresses into lib_Sum; a mismatch on a library not marked LIBF_CHANGED raises a recovery Alert(AN_LibChkSum), reported on stderr), with AddLibrary setting LIBF_SUMUSED and computing the initial sum and SetFunction keeping it current; RemLibrary (calls the library's own Expunge vector and, for a non-zero segList result, unlinks/unloads it like the CloseLibrary delayed-expunge path, while a zero result leaves it resident); AddResource/RemResource/ OpenResource on a real ExecBase.ResourceList (no built-in resources are modelled, so OpenResource of e.g. misc.resource returns NULL); and TypeOfMem, which classifies by address like a real machine: the first 2 MiB (including the reserved low region) is chip RAM (MEMF_PUBLIC|MEMF_CHIP), 2 MiB up to the end of guest RAM is fast (MEMF_PUBLIC|MEMF_FAST), and anything past the end of RAM is 0 (the chip range is capped when --ram is under 2 MiB). AllocMem still ignores the chip/fast flags, so which answer an allocation gets depends only on where the heap placed it. Interrupt servers and hardware access from a library's init (custom-chip registers) remain out of scope.
    • --fpsp-emulate (issue #129) — software-emulates the instructions a real 68060 removed from silicon (most FPU transcendentals — FSIN/FCOS/FATAN/FETOX/FLOGN/FMOD/FSCALE/FINT/ FGETEXP/FGETMAN/FSINCOS/... — plus a handful of integer ops: MOVEP, CHK2/CMP2, misaligned CAS/CAS2, 64-bit MUL/DIV) instead of taking a real "unimplemented instruction" exception for them, only meaningful together with --cpu 68060. Off by default, matching real 68060 hardware fidelity — without it, a 68040-FP-targeted binary traps the same way it would on real silicon, since volamos has no equivalent of 68060.library's boot-time (SetPatch) exception-vector patching to emulate them for every later process the way real AmigaOS does. The m68k crate backing this runtime already had both the real-hardware trapping behavior and a reference software implementation to fall back to (emulate_unimplemented_060); this just exposes the existing flag on volamos's own CLI. CLI-only, like --sanitize/--net/--clock-mhz — not a ~/.volamos/.volamos config key — and propagates to a nested System()/Execute()/ RunCommand() run the same way those do.
    • exec.library's SetFunction — patches a single library jump-table entry with a real JMP to guest code and returns a function pointer the caller can chain through to the original behavior, matching real SetFunction semantics. Previously deliberately out of scope (see docs/plan.md's 2026-08-19 gap audit) on the assumption it would need a "call back into guest code" primitive this runtime didn't have; it turns out not to need one — the entry just needs to stop being a host trap and become a real JMP, which the m68k backend already executes as ordinary guest code, the same trick crate::execlib::make_library's MakeLibrary already uses for a genuinely LoadSeged library's own vectors. The "old function" returned for a first-ever patch is a synthesized stub (a verbatim copy of the entry's previous bytes) rather than a bare sentinel, so a guest hook that calls through it to get default behavior — the common real-world SetFunction idiom — works, not just a bare patch/restore pair. Doesn't yet support patching an auto-created fake (vamos-escape-hatch) library's jump table, which lacks the real 6-byte-per-vector spacing a JMP abs.l needs. A patch only affects the single guest run that installed it — there's no persistence across separate volamos invocations or shared system-wide library state, so this is for testing a program's own hooking logic against itself, not emulating a real system-wide patch tool.
    • dos.library's CompareDates — compares two DateStamps field by field (ds_Days, then ds_Minute, then ds_Tick), returning a negative/zero/positive D0 the same way real CompareDates does. Was already in the LVO table but had no handler registered; closes that gap.
    • --libs-dir HOSTDIR — loads a real 68k library file from HOSTDIR instead of this runtime's own native implementation, for any library whose filename matches an Amiga library name exactly (e.g. HOSTDIR/utility.library), checked before this runtime's own native/fake library resolution. A library not found there falls back to normal resolution, unchanged; one found there but structurally invalid (no Resident/romtag, not RTF_AUTOINIT, ...) is a hard error, not a silent fallback to the fake-stub path -- useful for testing a program against a real library implementation (benchmarking a real utility.library against this runtime's own), or validating a replacement library (e.g. a custom graphics.library) against real guest programs. Deliberately opt-in and CLI-only, not a ~/.volamos/.volamos config key.

    0.9¶

    • --sanitize exits 99 on a violation, and no longer misreports a longjmp return as a stack-smash (issue #118). A longjmp returns through its setjmp slot, which a later call's frame may still occupy if nothing unwound it first — the check now recognizes a return landing on a reused slot instead of reporting it. Separately, a run that logged any violation now exits with status 99 instead of the guest's own exit code, so a harness that only checks the exit status doesn't pass a run that corrupted memory; a program started with System()/Execute() from inside the run still returns its own code to its caller.

    • The current task is now a real CLI process, and a bare System() command is looked up in C: (issue #117). The task previously had pr_CIS/pr_COS/pr_ConsoleTask all zero, so startup code reading them directly instead of calling Input()/Output() — DICE's does — ran with no stdin, stdout or stderr; SelectInput/SelectOutput now keep those fields in step. Separately, a System()/Execute() command with no volume was resolved only against the current directory, but the real shell also searches C: — SAS/C's sc invokes its linker as slink WITH ... and failed on exactly this.

    • Dispatch now recognizes task-struct corruption instead of misreporting it as stack bounds. check_stack_bounds reads tc_SPLower/tc_SPUpper fresh from guest memory on every dispatched trap, but a guest that overflows its stack without making a single library call in between can push A7 all the way down through the task struct before the next trap gets a chance to fire — by then the "bounds" it reads are stack debris, not real bounds, and the old message presented that debris as the task's stack and suggested a larger --stack, a knob that can't help. Inverted bounds (lower > upper) are unambiguous: no runtime code path ever produces them. The diagnostic now says what actually happened — the task struct was overwritten and the overflow predates this call — instead of printing garbage numbers as if they meant something. Found debugging a Rust/LLVM-m68k guest whose panic handler re-panicked forever (an LLVM M68k backend miscompile), descending ~16 MB of stack with no trap in between.

    • Loader: support HUNK_RELRELOC32 (0x3FD) (issue #116). Same on-disk shape as HUNK_RELOC32 (a uint32 count/hunk-number/offsets list), but the arithmetic is PC-relative rather than absolute: mem[loc] += target_hunk_addr - (this_hunk_addr + loc). Hit loading a real rustc-for-m68k-Amiga -fPIC-style binary that volamos previously rejected outright as an unrecognized hunk type.

    • Math libraries: condition codes extended to the basic arithmetic functions (issue #113). Follows up #112's SPCmp/SPTst fix: verified against real Kickstart 3.1 (40.68) via Copperline that mathffp.library's SPAdd/SPSub/SPMul/SPDiv/SPAbs/SPNeg/ SPCeil/SPFloor also set N/Z to match the result's actual sign/zero-ness, not just the compare/test functions. Added real regression coverage that branches on the condition codes directly (SAS/C's own idiom), since the existing tests only ever checked D0. IEEE single-precision arithmetic's flags were left alone pending follow-up — probing them on real hardware hit an unexplained crash partway through verification.

    • Math libraries: Cmp/Tst now set the condition codes (issue #112). IEEEDPCmp, IEEEDPTst, IEEESPCmp, IEEESPTst, SPCmp and SPTst returned their result in D0 only, but the real ROM also leaves it in the condition codes — and SAS/C's scmieee.lib branches on those without looking at D0, so every double comparison in a SAS/C program read as equal and exp() returned HUGE_VAL from its overflow check.

    • --clock-mhz reports native-handler call counts at exit (issue #109). Native library handlers (CopyMem, Write, ...) run in zero emulated cycles — a documented limitation — but a benchmark had no way to see how much of its work vanished that way. A third report line now itemizes it: total native calls, the top handlers by count, and the bytes CopyMem/CopyMemQuick moved. Prompted by a real GCC-codegen benchmark (AmigaPorts/m68k-amigaos-gcc#89) where a memcpy test "improved" 49% under volamos against 5% on real hardware — exactly the signature of copies disappearing into a zero-cycle native handler, and now diagnosable from volamos's own output.

    • CLI argument parsing migrated to clap (issue #101). User-visible improvements:

      • volamos --version works (long form only — -V stays --volume), prints to stdout, so V=$(volamos --version) does what you'd expect. Previously there was no version flag at all and the token was treated as a program path.
      • A mistyped flag before <program> is now a clean error with a did-you-mean suggestion (exit code 2) instead of surfacing as couldn't read '--sanitze': No such file or directory. A program file genuinely named with a leading - is still expressible as ./-foo or -- -foo.
      • --flag=value spellings now parse: --clock-mhz=25 (a reported failure), --stack=256K, and friends previously fell through to the catch-all and were treated as the program name.
      • --help output is generated from the flag declarations themselves (so it can't drift), grouped into Logging / Filesystem / Machine / Execution / Instrumentation / Networking sections.

    Everything after <program> still reaches the guest verbatim, even tokens spelled like volamos's own flags; config-file precedence is unchanged.

    **Breaking** — command lines that worked before and now behave
differently:

- A program path given bare with a leading `-` (`volamos -foo`) is
  now an unknown-flag error; spell it `./-foo` or `-- -foo`. (A
  deliberate trade: every *mistyped flag* used to be silently tried
  as a program path instead of being diagnosed.)
- A command-line parse error exits `2` (the conventional usage-error
  code) instead of `1`; `1` still means the parse succeeded but the
  run failed. Scripts testing for the specific value `1` on a bad
  invocation need updating.
- `--help` prints to stdout (and still exits `0`); it used to print
  to stderr.
- Diagnostic wording for parse errors is clap's, so anything
  matching the old exact stderr text needs updating.

    • --clock-mhz reports instruction and bus-access counts alongside emulated cycles (issue #107). A second stderr line at exit — instructions executed, bus accesses split into read/write, and the derived cycles-per-instruction and accesses-per-instruction ratios — makes a run's memory intensity visible from the run itself. volamos bills no bus wait states, so its emulated time is close to real hardware for arithmetic-bound code and very optimistic for bus-bound code — measured between 1.02x and 25x against cycle-paced hardware on real benchmarks (issue #105), and accesses-per-instruction is the number that says which end of that range a given workload sits at. read includes instruction fetch, so its floor sits a little above 1.0; write carries no fetch component and is the cleaner signal.

    • --clock-mhz reports total emulated cycles at exit (issue #104). Previously the cycle counter was only reachable indirectly — a guest had to call ReadEClock and report its own elapsed time, which works for an instrumented benchmark but leaves a plain binary unmeasurable, where vamos -v has printed an equivalent "total cycles:" line all along. The new exit line goes to stderr (so a harness parsing the guest's own stdout never sees it) and prints even when the run ends in an error. Cross-checked against vamos on the same binary: within 0.3%–1.0% agreement between the m68k crate's timing tables and Musashi's, two independently-implemented cycle models.

    • Added --clock-mhz: emulated time from ReadEClock (issue #102). Makes timer.device's ReadEClock report time derived from the CPU's own emulated m68k cycle count at a configurable rate, instead of host wall-clock time, so compiler A/B benchmarks under volamos are reproducible and independent of host load. Errors cleanly when combined with --sanitize (the cycle-counted run path never calls the sanitizer's per-instruction hooks, which would leave its shadow tracking silently stale) or an explicit --jit (the trace JIT never tracks a cycle count). GetSysTime/TR_GETSYSTIME/ DateStamp/CurrentTime are untouched; real hardware derives the E-Clock from chipset timing, not the CPU clock, so D0 always reports ECLOCK_PAL_HZ regardless of the configured rate.

    0.8¶

    • --sanitize no longer reports a recycled heap block as use-after-free (issue #95, reported by Bernie Innocenti). Once a run freed a block and the heap handed those same addresses back out, every write into the new allocation was reported against the old one's poison — one violation per byte, which slowed a BenchWork run from 10 seconds to 6 minutes and looked like a hang.

    The clearing now happens inside the guest heap, at the single point where a block leaves its control, and the allocator takes the address space as a parameter so a new allocation site cannot compile without it. That matters because AllocMem/AllocVec/AllocPooled are only 3 of some four dozen places that carve guest structures out of that heap — the FileHandle a dos Open returns, the FileLock a Lock returns, a ReadArgs argument buffer and many more — and any of them can be handed a poisoned block. Fixing only the exec allocators left a guest that freed a large block and then opened a file still reporting 46 phantom use-after-free writes.

    Separately, --sanitize's slowdown on a violation-heavy run is gone: the per-byte access check was deciding "did that byte report?" by summing the hit counts of every violation already logged, so the cost grew with the log. A 400,000-violation run goes from 1.33s to 0.03s, with identical output.

    • --ram above 16 MiB is now refused on a 68000/68010 (issue #98) instead of producing a program that dies confusingly later. Those CPUs have a 24-bit address bus, and the guest stack sits at the top of the address space, so --ram 32M on the default --cpu 68000 put the stack pointer at an address the CPU cannot express: it wrapped, a JSR into a library pushed its return address into low memory, and the RTS popped whatever was there — surfacing several calls later as "continuation stub trapped at 0x000000c4 with no pending continuation", which points at nothing useful. It now fails up front naming both flags, the way an oversized --stack already did. Pass --cpu 68020 (or later) for a 32-bit address bus. The default --ram is exactly 16 MiB, so only a raised --ram was ever affected.

    • pr_Arguments is now populated on the fake struct Process. A0/D0 carry the command-line buffer at process entry, but real AmigaOS exposes the same string again through pr_Arguments, and volamos left that field permanently NULL. Found running the real sidick/micropython Amiga port, whose startup reads argv from pr_Arguments rather than A0/D0: it saw "no arguments" and dropped into its REPL even when a script path was passed.

    • AllocDosObject/FreeDosObject now support DOS_FIB — a zeroed struct FileInfoBlock, the same shape as the already-supported DOS_RDARGS and DOS_EXALLCONTROL. Also found via the micropython port, whose os.walk() allocates its own FileInfoBlock this way instead of using ExAll.

    • SetVar(name, NULL, ...) on a variable that does not exist now succeeds silently, as real SetVar does — and so does DeleteVar, which is implemented in terms of it. Both the local-variable path and the ENV:-backed global one were returning ERROR_OBJECT_NOT_FOUND. Verified against real Kickstart.

    • OpenLibrary now ignores garbage in the high word of the requested version, matching the CMP.W real ROMs use: a caller passing $30000000 in D0 gets the library, where volamos previously compared all 32 bits and refused. Found via a recent AROS fix ("Frontier 2") that identified the same divergence in AROS; volamos had been reproducing the bug rather than the hardware. D0 itself is left untouched for the Open vector, as on real hardware.

    0.7¶

    • The heap detectors now cover four more allocators (issue #83, tier 0): utility.library's AllocateTagItems, dos.library's AllocDosObject, and exec.library's CreateIORequest and CreateMsgPort, plus their matching free calls. All four carve from the same guest heap as AllocMem, so redzone space was already being reserved for them whenever --sanitize was on — only the shadow marking was missing, which meant a guest overrunning a FileInfoBlock, an RDArgs, a MsgPort or a TagItem array that volamos handed it went unreported.

    It found a real bug on the first sweep: the PhxAss assembler asks CreateIORequest for 40 bytes (sizeof(struct timerequest)) and then reads two bytes one past the end. Harmless on real hardware, where that read lands in whatever follows on the heap, which is exactly the class of latent bug this exists to surface. So PhxAss is no longer silent under --sanitize — that one report is expected; --sanitize-ignore-pc silences it if you want a clean baseline.

    Still not covered: exec.library/Allocate, where the guest owns the memory pool, and which is where a C runtime's malloc actually sub-allocates.

    • Diagnostics now name the source location (issue #74). Sanitizer violations are annotated with file:line when the program carries a HUNK_DEBUG LINE block (SAS/C's DEBUG=LINE, PhxAss's LINEDEBUG), falling back to symbol+offset from HUNK_SYMBOL otherwise, and to the bare address when a binary carries neither. The raw PC is always kept alongside, since that is what a disassembly needs.

    Worth knowing what this does and doesn't reach: m68k-amigaos-gcc emits stabs debug info, which isn't decoded, so -g alone doesn't give file:line — but gcc binaries do carry symbols, so a real gcc-built stack-smash now reports expected 0x00002b40, found 0x41414141 ... (at ___main+0x3c). static functions never appear in a symbol table, so attribution inside one falls to the nearest exported symbol.

    Also new: fixtures/linetest, a repo-owned binary carrying real LINE data (PhxAss-built, since amiga_asm.py can't emit debug hunks), so the parser's tests don't depend on artefacts that vanish.

    • Added --dirty-heap (issue #80): fills every allocation made without MEMF_CLEAR with 0xA5 instead of leaving it zeroed, so a guest that relies on uncleared memory being zero fails here the way it can on real hardware — where AllocMem returns whatever debris was there. MEMF_CLEAR allocations are untouched. Deliberately independent of --sanitize, because this one changes what the guest sees rather than only observing it, and --sanitize's never-perturb-the-program property is worth protecting (re-verified: the real SAS/C compiler's output object file is still byte-identical under --sanitize).

    This also settled a verdict --sanitize-uninit had to leave open: the real PhxAss assembler reads an uninitialized field from a ~568-slot table, and with the fill on its output is byte-identical (checked on a 60-symbol source as well as a trivial one), so it does not act on those values. Benign, not a latent bug.

    • Added --sanitize-uninit (issue #68): opt-in uninitialized-read detection on top of --sanitize, plus --sanitize-ignore-pc for silencing a site you have already triaged. Byte-granular, so a partially-initialized structure is caught rather than being treated as initialized because something in it was written; MEMF_CLEAR allocations never report.

    Getting the false-positive rate usable was the bulk of the work, and it turned on two latent bugs that were harmless only because uninit reporting was off: a below-stack-pointer write forgiven by the grace band returned without healing the byte, so the value a JSR had just pushed read back as never-written; and stack growth blanket-marked the newly-exposed range uninitialized, clobbering the bytes the very instruction that moved the stack pointer had just written (a push writes as it decrements). Together those took real pLhA listing a 102-file archive from 109,204 reports to zero, and every fixture to zero.

    Violation reports now also group by PC: a site with many violations collapses to one line with a count and address range, while a site with few prints each violation in full — so a corrupted return address never loses its expected/actual pair, which is its entire diagnostic value. Real PhxAss goes from a wall of 574 lines to 6 legible sites, one of which accounts for 568 of them.

    0.6¶

    • Added --sanitize, a valgrind/ASan-style memory sanitizer (issue #65). m68k-amigaos-gcc has no -fsanitize=address, and MMU-based tools like MuForce are page-granular, so single-byte heap overruns and use-after-free went undetected. volamos can do better because it is the allocator and every guest access already funnels through one trait: a shadow byte per guest byte now backs poisoned redzones either side of every AllocMem/AllocVec/AllocPooled block (including the alignment padding), plus a free quarantine that keeps a freed address out of circulation so use-after-free can't hide behind an address nothing happened to reuse. Host-side library handlers write guest memory through the same checked path, so bad buffers passed to dos.library calls are caught with no per-function instrumentation. Violations are reported to stderr, deduplicated with hit counts, and never abort the guest -- a detector, not an enforcer. Two things worth knowing: --sanitize forces the JIT off, because its raw-pointer fast path bypasses the checks entirely (a sanitized JIT run would look clean no matter what the program did); and overflows within a single stack frame remain invisible, exactly as they are to valgrind, since catching those needs compiler instrumentation. New fixtures/memtest exercises all of it, and is the first fixture whose .s is assembled by the real PhxAss running under volamos itself.

    • Extended --sanitize to stack bugs (issue #65, increment 2): accesses below the stack pointer, and return-address corruption via a shadow call stack that records what each JSR/BSR pushed and verifies it at the matching return — stack-smash detection valgrind itself doesn't offer. Getting this to zero false positives on real software was most of the work: a push writes below the stack pointer by definition, so a 64-byte grace band (sized to MOVEM's worst case, the same window valgrind forgives) is needed or every subroutine call reports; volamos performs library-call returns itself rather than executing an RTS, so dispatch has to retire shadow frames explicitly or a stale frame sits exactly where the next push lands; and StackSwap abandons a whole stack, so both the stale poison and the pending call frames have to be cleared or the replacement stack's reused addresses produce bogus reports. Real PhxAss, real pLhA and the real SAS/C 6.58 compiler now all run clean, with sc's object file byte-identical to an unsanitized run's. New fixtures/stacktest covers both detectors plus three false-positive guards.

    0.5¶

    • Fixed the guest command-line buffer's missing trailing space (issue #63): whenever a launched program has at least one argument, real AmigaOS's own command-line buffer carries a trailing space before the final '\n' ("foo bar baz \n", not "foo bar baz\n") -- confirmed directly against real Kickstart 2.0/3.0/3.1 hardware via a new local, real-Kickstart comparison harness (tools/compare_kickstart_versions.py, using Copperline's copperhf.device). Kickstart 3.2 alone doesn't add it -- a real, intentionally-untouched AmigaOS version difference, not a bug (this project targets 3.1 first). Also fixed a real bug found along the way in fixtures/echoargs.s/libcall.s: A0 is a scratch register across any library call (real Kickstart's OpenLibrary clobbers it; volamos's own doesn't), so reading the command-line pointer back from A0 after an OpenLibrary call is real-hardware-unsafe even though it happened to work under volamos.
    • Implemented mathieeesingbas.library/mathieeesingtrans.library: the single-precision IEEE math libraries, previously only a fake OpenLibrary stand-in with no real function support. Mirrors mathieeedoubbas.library/mathieeedoubtrans.library function-for- function on plain f32 instead of f64. Fixed a real bug found via amitools' own math_single_trans ground truth along the way: IEEESPPow's result is y raised to the x power (IEEESPPow(3.0, 4.0) -> 64.0 = 4**3), not x raised to y as a naive reading of its .conf-derived argument names would suggest -- tracing this down also revealed mathieeedoubtrans.library's existing IEEEDPPow already had the equivalent (correct) behavior, just a misleading doc comment, now corrected.

    0.4¶

    • Fixed mathffp.library/mathtrans.library's FFP encoding (issue #53): the sign bit and exponent field were in swapped bit positions (an old bug hidden by a unit test that re-derived the same wrong layout from this module's own -- also wrong -- doc comment instead of checking against real hardware), and overflow/underflow/ domain-error (NaN) results weren't saturating correctly. Found via a new local comparison harness against amitools' own test corpus (tools/compare_amitools_suite.py); took the affected tests' divergence from vamos from the large majority of their output lines down to a handful of residual, believed-benign ones (a single overflow-boundary edge case and ordinary cross-implementation transcendental-function rounding variance). Both since confirmed against real Kickstart 3.1 hardware: the overflow-boundary case (SPMul saturating exactly at FFP's maximum exponent field) was correct as fixed, and two more real bugs turned up in the same pass -- RawDoFmt/VPrintf's %x/%lx printed lowercase hex where real hardware prints uppercase (issue #48), and IEEEDPCeil() returned -0.0 for a ceil-to-zero result where real hardware (matching vamos) returns +0.0 (issue #51, originally misdiagnosed as correct IEEE-754 behavior on volamos's side and vamos's divergence -- backwards). Also confirmed that mathieeedoubbas/ mathieeedoubtrans's positive-signed NaN convention for domain-error results (0/0, out-of-domain acos/asin/log/etc.) matches real hardware and vamos's negative-signed convention is vamos's own divergence (issue #52), and canonicalized an internal inconsistency where Rust's own f64::asin/acos didn't agree with themselves on NaN sign for symmetric out-of-domain inputs.
    • Fixed RawDoFmt's %b (BSTR) format (issue #45): the data-list entry for %b is a BPTR, not a raw byte address, so it needs the same << 2 conversion dos.library's own BPTR-taking calls already apply -- confirmed against real Kickstart 3.1 hardware and amitools' own exec_rawdofmt test (BStr: 'Hoi!', previously garbled).
    • Fixed Seek() not rejecting an out-of-range target position (issue #47): a host file's own seek() happily allows seeking arbitrarily far past end-of-file (standard POSIX behavior), but real Seek()'s own NDK autodoc says "you cannot Seek() beyond the end of a file." The target position is now computed and validated against the file's actual length (and against a negative result) before touching the host file at all, matching -1/ERROR_SEEK_ERROR, the modern (post-V39) contract -- not the old, documented-as-fixed pre-V39 behavior of returning the current position instead, which amitools' own dos_seek test still (incorrectly, for a V40 target) expects since it's a literal vamos-captured assertion, not real hardware.
    • Implemented dos.library/FindArg (issue #55): finds the zero-based slot index a keyword names in a ReadArgs-style template (or -1), reusing the same template parser and NAME=ABBREV alias handling ReadArgs itself already had. Previously an unhandled library call.
    • Fixed AnchorPath's ap_Buf qualification (issue #46): confirmed via real Kickstart 3.1 hardware (through a genuine in-memory FFS/OFS volume synthesized from a host directory, not just a convenience boot mount) that ap_Buf tracks whatever device/path qualification the caller's own MatchFirst/MatchNext pattern text had -- a device-qualified pattern ("sys:") reports device-qualified entries ("sys:c"); a bare, current-directory-relative pattern with no prefix at all reports entries with no qualification either, matching fib_FileName exactly. volamos previously always stripped ap_Buf down to a bare relative name regardless (issue #14's own fix, which turned out to be treating a symptom rather than the actual mechanism -- see #46's closing comment for the full story).
    • Fixed AnchorPath's volume-root fib_FileName (issue #58): a MatchFirst/MatchNext report for a bare volume root now has a blank fib_FileName, matching real Kickstart 3.1 hardware -- a distinct convention from plain Lock()/Examine() on the same volume root, which correctly keeps reporting the volume name.
    • Built-in standard-volume defaults (issue #43): SYS:, RAM:, and the standard C:/S:/LIBS:/DEVS:/ENVARC:/T:/ENV: assigns onto them now resolve out of the box, with zero -V/-a configuration needed — backed by empty host directories created only on first actual use (SYS: persists across runs under --volumes-dir/VOLUMES_DIR, default ~/.volamos.d/volumes; RAM:/T:/ENV: are a fresh, unique-per-process temp directory, removed automatically once the run ends — never shared between, or surviving past, a single volamos invocation). An explicit -V/-a for the same name always overrides the matching default, so -V SYS:~/amiga/wb31 brings that volume's own real C:/Libs:/etc. along with it rather than the synthetic skeleton reappearing underneath it. --no-defaults/DEFAULTS=false restores the original "nothing configured means no filesystem at all" behavior. Only these specific real-AmigaOS names are covered — unlike vamos's broader auto-assign machinery, a genuinely unknown/typo'd volume name still fails loudly with an IoErr(). See Volumes and Assigns.
    • Program-directory config file (issue #16): a .volamos next to the launched binary (in <program>'s own containing directory) is now consulted between ./.volamos and ~/.volamos, so a toolchain installation can carry its own volume/CPU settings and be invoked from anywhere. Behavior change: relative VOLUME/AUTO_ASSIGN paths in any config file now resolve against that file's own directory instead of volamos's process working directory — an existing ~/.volamos or ./.volamos using relative paths resolves differently if its directory isn't where you invoke volamos from (CLI-supplied relative paths are unchanged). See Configuration.
    • Parent-step (a//b) fidelity: a parent step that climbs above the volume root now fails like a missing object instead of being clamped at the root — the root has no parent, matching real FFS behavior as verified in amitools PR #7's writeup (vamos made the same change there). Lock names reported back to the guest (NameFromLock()) now also carry the volume/assign name in its configured spelling (Lock("sys:foo") names itself SYS:foo), completing the canonical-path treatment their components already got (parent steps collapsed, on-disk case).
    • ExAll/ExAllEnd: the batched directory scanner libnix's readdir() (and so most gcc-built programs that scan a directory) is built on, including continuation across calls via eac_LastKey, eac_MatchString pattern filtering, all ED_NAME..ED_OWNER entry levels, and AllocDosObject/FreeDosObject support for DOS_EXALLCONTROL. Before this, ExAll was an unhandled call, so every directory looked empty to readdir()-based programs. Mirrors amitools PR #8, which added the same to vamos.

    0.3¶

    • Interpreter and release-build performance: FlatMemory's multi-byte reads/writes now do a single bounds check plus a native big-endian load/store instead of decomposing into repeated byte-level calls, and the non---jit execution path now runs through the m68k crate's run_batch (batch size 1) instead of looping its plain step, picking up run_batch's non-cycle-accurate bus mode and raw-pointer fast-memory access — same per-instruction granularity, no observable behavior change. Release builds also gain lto = true/codegen-units = 1. On a real CoreMark 1.0 run, this took the interpreter from 105.9 to 198.2 iterations/sec (~1.9x) and --jit from 445.1 to 537.1 (~1.2x) — see the CLI Reference's --jit note for the full comparison table, including vamos's 270.6 on the same binary.
